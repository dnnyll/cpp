2. RECURSION TREE - ONLY THE *LARGER* HALF RECURSES
--------------------------------------------------------------------------------
n=15  [38, 3, 9, 81, 47, 12, 5, 71, 66, 2, 29, 44, 18, 91, 53]
       pairs (3,38)(9,81)(12,47)(5,71)(2,66)(29,44)(18,91)  straggler=53
       v recurse on the 7 LARGER values only
  n=7   [38, 81, 47, 71, 66, 44, 91]
         pairs (38,81)(47,71)(44,66)  straggler=91
         v recurse on the 3 LARGER values only
    n=3   [81, 71, 66]
           pairs (71,81)  straggler=66
           v recurse on the 1 LARGER value only
          \- base [81]
           ^ returns [66, 71, 81]
         ^ returns [38, 44, 47, 66, 71, 81, 91]
       ^ returns [2, 3, 5, 9, 12, 18, 29, 38, 44, 47, 53, 66, 71, 81, 91]

15 -> 7 -> 3 -> 1.  Halves every time, so O(log n) depth. Smalls never recurse
and never get compared to each other - that's where the win comes from.


3. ONE CALL, ANNOTATED
   ([5, 3, 9, 1, 7, 2, 8], output verified against the real `make trace` build)
--------------------------------------------------------------------------------
sortVector([5, 3, 9, 1, 7, 2, 8])
|
+- step1  PAIR                                    pairVector()
|     input   5  3  9  1  7  2  8
|     -------------------------------------------  swap each so small <= large
|     pairs  (3,5) (1,9) (2,7)      straggler = 8   <- odd count
|     smalls [3, 1, 2]     larges [5, 9, 7]
|
+- step2  RECURSE on larges only   -> [5, 7, 9]
|     (inner call: pair (5,9), straggler 7,
|      recurse [9] -> [9], front-insert 5 -> [5,9],
|      straggler 7 -> [5,7,9])
|     mainChain = [5, 7, 9]
|
+- step3  RANK each small in mainChain             std::lower_bound
|        the rank is computed ONLY to detect which value can skip the search
|        3 -> index 0    1 -> index 2    2 -> index 1
|        pending = [(3,0) (1,2) (2,1)]
|
+- step4  FRONT-INSERT SHORTCUT    the (x, 0) needs no search
|     mainChain.insert(begin(), 3)
|     [3, 5, 7, 9]              pending = [(1,2) (2,1)]
|
+- step5  JACOBSTHAL ORDER for the 2 survivors
|     g = [0,1] -> [0,1,1,3]      order = [1, 2]   (1-based slots)
|     slot 1 -> value 1 -> lower_bound -> index 0 -> [1, 3, 5, 7, 9]
|     slot 2 -> value 2 -> lower_bound -> index 1 -> [1, 2, 3, 5, 7, 9]
|
+- step6  STRAGGLER LAST, exactly like everything else
        binaryInsert(8) -> index 5 -> [1, 2, 3, 5, 7, 8, 9]   [ok]


4. WHY THERE IS NO INDEX SHIFT
--------------------------------------------------------------------------------
Step 3 stores a rank for each small value, and step 4 grows the chain by one at
the front. The textbook Ford-Johnson then bumps every stored rank by +1,
because in a textbook implementation the remembered rank is what positions the
insert:

  before front-insert     pending ranks point at:
    mainChain [5, 7, 9]    1 -> index 2   2 -> index 1
          ^ insert 3 here
  after front-insert
    mainChain [3, 5, 7, 9] 1 -> index 3   2 -> index 2
                           \-- both moved right by one --/

THIS CODE DOES NOT DO THAT, AND MUST NOT. binaryInsertVector is handed only the
VALUE, never the stored rank, and re-searches the whole chain from scratch:

  binaryInsertVector(mainChain, smallerValues[index].first);
                                              ^^^^^^ .first only
                                              (.second is never passed)

So the rank is dead the moment the front-insert test has consumed it. The +1
loop existed in this codebase but was unreachable code: it wrote a field nobody
read. It has been removed. Note the same applies to the front-insert itself -
it is a pure optimisation, and dropping it entirely would still give correct
output, just slower.

The general lesson: a stored index is only safe to reuse if nothing re-derives
the position. Once every insert re-searches, the index is pure overhead.


5. JACOBSTHAL NUMBERS
--------------------------------------------------------------------------------
g(0)=0  g(1)=1  g(k) = g(k-1) + 2*g(k-2)
      0, 1, 1, 3, 5, 11, 21, 43, 85, ...

n = 16  ->  insertion order (1-based slots):
          1, 3, 2, 5, 4, 11, 10, 9, 8, 7, 6, 16, 15, 14, 13, 12
          | | | |  |  |   |-------||-------|  |------|------|
            fill 1st, then straddle it, then straddle again,
            doubling the contiguous block each round

The *intent*: once slot 1 is placed, slot 3 is inserted somewhere near it, so
slot 2's search window is squeezed between them. Repeat, and each new element
only ever searches a tiny window. That intent only pays off if the search is
bounded by those neighbours - this code doesn't, hence the cost analysis in
section 7.


6. binaryInsertVector - LOCATE, THEN ONE SINGLE INSERT
--------------------------------------------------------------------------------
chain = [1, 3, 5, 7, 9]      insert 2

  lo=0 hi=5, mid=2 -> chain[2]=5, 5 >= 2 so hi=2
  lo=0 hi=2, mid=1 -> chain[1]=3, 3 >= 2 so hi=1
  lo=0 hi=1, mid=0 -> chain[0]=1, 1 <  2 so lo=1
  lo==hi -> position 1

  3 comparisons, then ONE insert. Never std::sort, never a linear scan.
  chain.insert(chain.begin() + 1, 2);   ->  [1, 2, 3, 5, 7, 9]

  Note low starts at 0 and high at chain.size() on every single call - the
  search is never narrowed using a remembered position. That is exactly why
  the stored rank in step 3 turned out to be dead.

For the deque it's the identical search plus std::deque::insert - which is why
the two timings are comparable.


7. HONEST COST SUMMARY
--------------------------------------------------------------------------------
+-----------------------------------------------+
| Recursion depth      O(log n) - verified 15->7->3->1
| Comparisons/level    one lower_bound per small value = O(log n)
| Total comparisons    O(n log n), measured ~ n*log2(3n),
|                      *independent of insertion order*
| Element moves        const + inversions, NOT minimised by
|                      Jacobsthal order here
| Straggler            always last, O(log n)
| Duplicate check      O(n^2) in parsing - the one real
|                      weakness, still deferred
+-----------------------------------------------+


WHAT TO ACTUALLY SAY WHEN YOU EXPLAIN IT
--------------------------------------------------------------------------------
It pairs the numbers up and normalises each pair so the smaller one comes
first. Then it recurses only on the larger halves, which halves the problem
each time, so the recursion is only log-deep and the small elements never get
compared with each other. Coming back up, it binary-searches each small value
to find where it belongs, front-inserts any value that belongs at position 0 as
a free shortcut, then binary-inserts the rest - in Jacobsthal order - followed
by the leftover straggler. Every insert re-searches the chain from scratch, so
nothing has to be re-indexed when the chain grows. It's run twice, once per
container, and both are timed. The deque goes first because the vector sort
consumes the unsorted input.

Two things NOT to claim: that Jacobsthal makes it faster (it doesn't here), and
that it's a stable or in-place sort (it isn't - it copies and allocates).
